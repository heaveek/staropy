## 1. Продукт и цель

Создать платное Telegram Mini App для раскладов Таро. Пользователь открывает приложение из Telegram, выбирает расклад и тему, задаёт необязательный вопрос, получает карты и интерпретацию, затем может открыть историю.

Цель — автоматизированный онлайн-продукт с низкими эксплуатационными затратами, который сопровождает один backend-разработчик.

Принципы:
- колода Rider–Waite–Smith;
- никаких AI-вызовов для трактовки;
- значения карт, тексты позиций, шаблоны итогов и редакционные сочетания хранятся в структурированной БД;
- алгоритм выбирает блоки по явным правилам и соединяет шаблонами;
- карты вытягивает backend;
- результат сохраняется как snapshot и не меняется при обновлении контента;
- система работает на слабом сервере без GPU;
- трактовка — инструмент саморефлексии и развлечения, не гарантированное предсказание и не замена профессиональной консультации.

Не входит в MVP: AI-генерация, несколько стилей трактовки (отложены до появления дохода), пользовательские колоды, социальная сеть, сложная CMS, микросервисы, массовая генерация неподтверждённых связей ради количества.

## 2. Продуктовые решения

### 2.1. Пять раскладов

| Код | Название | Карт | Доступ |
|---|---|---:|---|
| `daily_card` | Карта дня | 1 | Бесплатный дневной лимит |
| `yes_no` | Да / Нет | 1 | Бесплатный дневной лимит |
| `past_present_future` | Прошлое — Настоящее — Будущее | 3 | Бесплатный дневной лимит |
| `situation_advice_outcome` | Ситуация — Совет — Итог | 3 | Бесплатный дневной лимит |
| `celtic_cross` | Кельтский крест | 10 | Только Premium |

Один бесплатный расклад в день означает один бесплатный запуск любого обычного расклада на пользователя за календарный день, а не по одному каждого вида. Кельтский крест всегда требует Premium. Часовой пояс задаётся `APP_TIMEZONE`, по умолчанию `Europe/Moscow`; дату лимита рассчитывает backend.

### 2.2. Темы

- `love` — Любовь и отношения.
- `work` — Работа и карьера.
- `money` — Деньги и ресурсы.
- `self_development` — Саморазвитие.

Тема влияет на выбор текста, но не фильтрует колоду.

### 2.3. Бесплатный доступ и Premium

Free:
- один бесплатный запуск обычного расклада в день;
- ограниченная история;
- без Кельтского креста.

Premium:
- неограниченные расклады;
- Кельтский крест;
- полная история.

`FREE_HISTORY_LIMIT` по умолчанию 3 последних результата. Ограничение проверяет сервер.

Цена и сроки Premium не утверждены. Не зашивать придуманные цены. Тарифы задаются через БД/seed или конфигурацию. Предпочтительный платёжный путь — Telegram Stars для цифрового продукта внутри Telegram; перед production проверить актуальные требования Telegram. Если тарифы или секреты не настроены, показывать, что покупка пока не настроена.

### 2.4. Основной сценарий

1. Пользователь запускает бота и открывает Mini App.
2. Backend проверяет Telegram `initData` и создаёт/обновляет профиль.
3. Главная показывает расклады, Premium-статус и остаток лимита.
4. Пользователь выбирает расклад, тему и необязательный вопрос (500 символов по умолчанию).
5. Backend проверяет права и лимит.
6. Backend выбирает карты, собирает трактовку и сохраняет результат в транзакции.
7. Frontend показывает анимацию раскрытия и результат.
8. История возвращает прежний snapshot, не пересчитывает его.

## 3. Технологии

- Backend: Python 3.11+ (предпочтительно 3.12), FastAPI, Pydantic.
- ASGI: Uvicorn.
- БД: PostgreSQL.
- ORM/миграции: SQLAlchemy 2.x + Alembic.
- Redis: необязателен для rate limit/временных задач; приложение должно работать без него, если не используется.
- Frontend: React + TypeScript + Vite.
- Стили: Tailwind CSS.
- Анимации: Framer Motion при совместимости с версией React.
- Telegram Mini App: Telegram Web Apps API с типизированной обёрткой.
- Бот: Python + aiogram.
- Backend tests: pytest + httpx/TestClient.
- Frontend tests: Vitest + React Testing Library.
- Деплой: Docker Compose, если подходит серверу; допустим systemd.
- Логи: Python logging, без токенов, полной `initData` и лишнего пользовательского текста.

Не добавлять AI-провайдеры, векторные БД, брокеры сообщений и микросервисы.

Архитектура: Telegram Client → React Mini App → HTTPS REST API/FastAPI → PostgreSQL. Бот обеспечивает `/start`, `/help`, кнопку открытия Mini App и опциональные добровольные уведомления.

Правила кода:
- разделять API, доменную логику, репозитории и интеграции;
- timezone-aware даты, PostgreSQL `timestamptz`;
- денежные значения целочисленные, не `float`;
- миграции Alembic обязательны для production;
- единый формат API-ошибок;
- snapshot достаточен для отображения старого результата;
- бизнес-логика не должна зависеть от Redis.

## 5. Telegram-аутентификация и безопасность

### 5.1. Mini App auth

- Frontend отправляет исходную строку `Telegram.WebApp.initData`.
- Backend проверяет подпись по официальному алгоритму Telegram Web Apps с HMAC-SHA-256 и bot token.
- Проверяет `auth_date` и максимальный возраст через конфигурацию.
- Только после проверки получает Telegram ID и создаёт/обновляет пользователя.
- `initDataUnsafe` не является доказательством подлинности.
- Не логировать полную `initData`.
- Development auth допустим только в явном режиме разработки и запрещён в production.

### 5.2. Безопасность

- HTTPS в production, CORS ограничен доменом Mini App.
- Внутренний user ID — UUID/bigint; `telegram_id BIGINT UNIQUE`. Username не использовать как идентификатор.
- Валидировать типы/длины входных данных.
- Rate limit для создания раскладов и платежей.
- Не доверять клиентским `is_premium`, лимитам, цене, `user_id` и `card_ids`.
- Платёжные callback проверять официальным способом.
- Повторный запрос не должен списывать лимит или создавать entitlement дважды.
- Использовать idempotency key для создания расклада или равноценную серверную защиту.
- Не выдавать SQL/stack trace/секреты клиенту.

## 6. Колода и контент

### 6.1. 78 карт Rider–Waite–Smith

ID и коды стабильны:
- Старшие Арканы ID 1–22.
- ID 1 — Шут, `number=0`.
- ID 2 — Маг.
- ID 22 — Мир, `number=21`.
- Жезлы ID 23–36.
- Кубки ID 37–50.
- Мечи ID 51–64.
- Пентакли ID 65–78.

Поля: `id`, `arcana` (`major`/`minor`), `suit` (`NULL` для старших, `wands/cups/swords/pentacles` для младших), `number`, уникальный `code`, `name_ru`, `name_en`, nullable `image_url`, `is_active`, timestamps при необходимости.

Младшие ранги: 1 Туз; 2–10 числовые; 11 Паж; 12 Рыцарь; 13 Королева; 14 Король.

Проверить ровно 78 карт, уникальные ID/коды, корректные масти и номера. Не включать изображения без проверки лицензии; до этого показывать placeholder.

### 6.2. Теги

Ориентир — около 150 тегов, не создавать теги ради количества. Категории: события, эмоции, отношения, карьера, финансы, духовность, действия, препятствия, личность, энергия, время, результат.

`tag_categories`: `id`, `code`, `name_ru`, `description`, `sort_order`.

`tags`: `id`, `code UNIQUE`, `name_ru`, `category_id`, `description`, `is_active`, `created_at`.

`card_tags`: `card_id`, `tag_id`, optional `weight`, `source` (`editorial`/`generated`), `review_status` (`approved`/`needs_review`/`rejected`), UNIQUE(`card_id`,`tag_id`).

Вес — это вес соответствия, не доказанная истинность значения.

### 6.3. Значения карт

Значения различаются по карте, теме (nullable для универсального), роли/типу и, при необходимости, ориентации. В MVP перевёрнутые карты выключены; ориентация `upright`.

`card_meanings`:
- `id`, `card_id`, `theme_id` nullable;
- `meaning_type` (`general`, `resource`, `challenge`, `advice`, `outcome` и т. п.);
- `text_short`, `text_long`, `priority`;
- `is_active`, `review_status`, `content_version`, timestamps.

`meaning_tags`: `meaning_id`, `tag_id`, optional `weight`.

Тематический блок приоритетнее универсального. Выбирать один подходящий блок каждого нужного типа, а не склеивать все совпадения.

### 6.4. Отношения карт

Типы: `supports`, `weakens`, `opposite`, `similar`, `develops_into`, `blocks`, `complements`, `warns_about`, `transforms`, `amplifies`.

`card_relations`: `id`, `source_card_id`, `target_card_id`, `relation_type`, `strength` 1–10, `is_directional`, nullable `theme_id`, nullable `interpretation_text`, `source`/`editorial_note`, `is_active`, `review_status`.

Правила:
- не делать связи симметричными автоматически;
- `develops_into` направленная;
- симметричность остальных типов задаётся явно;
- для направленной связи не создавать обратную;
- исключить дубли и self-links без специального правила;
- эвристические связи маркировать `needs_review`;
- runtime показывает только активные одобренные связи;
- отсутствие связи — нормальный случай.

### 6.5. Комбинации

`card_combinations`: `id`, `card_a_id`, `card_b_id`, `combination_type`, nullable `theme_id`, `text`, `priority`, `is_directional`, `is_active`, `review_status`.

Для симметричной пары нормализовать `(min(card_id), max(card_id))`; для направленной сохранять порядок. Не описывать все возможные пары заранее. При отсутствии точной комбинации просто не добавлять этот блок.

### 6.6. Шаблоны

`interpretation_templates`: `id`, nullable `spread_id`, nullable `theme_id`, `template_type` (`opening`, `position`, `summary`, `advice`, `disclaimer`), `template_text`, `priority`, `is_active`, `review_status`.

Разрешены только заранее определённые безопасные placeholders; не выполнять код из шаблона.

## 8. Вытягивание карт и лимит

1. Проверить активность расклада/темы и доступ.
2. Проверить Premium/дневной лимит.
3. Получить активные карты на backend.
4. Вытянуть нужное количество уникальных карт без повторов (`secrets` или `random.SystemRandom`).
5. В MVP все карты `upright`.
6. Сопоставить с позициями, собрать интерпретацию.
7. Сохранить результат и usage в одной транзакции.

«Карта дня» — обычный расклад, расходующий общий бесплатный лимит. Повторное открытие сохранённой карты дня не создаёт новый результат.

`daily_usage`: `id`, `user_id`, `usage_date DATE`, `free_readings_used INTEGER`, `updated_at`, UNIQUE(`user_id`,`usage_date`).

Проверка и расход лимита должны быть атомарными: условный insert/update или блокировка в транзакции. Нельзя делать простой `COUNT`, затем `INSERT` без блокировки. Покрыть параллельные запросы тестом. Premium не расходует лимит. Неудачная операция без созданного расклада лимит не списывает.

## 9. Движок интерпретаций без ИИ

### 9.1. Вход и выход

Вход: код расклада, тема, вопрос, карты, позиции, одобренные значения, отношения/комбинации, версия контента.

Выход: краткое резюме, текст каждой позиции, необязательные редакционные сочетания, общий итог, подготовленные рекомендации и дисклеймер.

Движок не пишет новые предложения. Вопрос пользователя сохраняется и отображается как контекст; он не передаётся AI и не используется как инструкция. Экранировать HTML.

### 9.2. Приоритет выбора значения

Для карты/позиции:
1. активное одобренное значение точной темы и подходящей роли;
2. активное одобренное значение точной темы общего типа;
3. универсальное одобренное значение подходящей роли;
4. универсальное одобренное значение общего типа;
5. нейтральный fallback с названием карты и сообщением, что текст для этого сочетания ещё готовится.

Учитывать `priority`. Не склеивать все совпавшие тексты.

### 9.3. Сборка позиции

Для каждой позиции выбрать один основной смысл; при наличии добавить ролевой блок и максимум одну проверенную релевантную комбинацию. Не дублировать смысл. Пример структуры:
> **{position_name}: {card_name}**  
> {selected_meaning_text}  
> {optional_combination_text}

Это структура, а не готовая эзотерическая трактовка.

### 9.4. Итог

Использовать подготовленный summary для расклада/темы. Если его нет — нейтрально собрать итог из кратких резюме позиций шаблоном. Не представлять это как доказанное предсказание. Не повторять один и тот же блок повсюду. Комбинации необязательны; разумно ограничить их одной на позицию и двумя в общем итоге.

### 9.5. Да / Нет

`yes_no_meanings`: `card_id`, `answer` (`yes`/`no`/`maybe`), `text`, nullable `theme_id`, `priority`, `is_active`, `review_status`. Точная тема приоритетнее универсальной. Нет записи — `maybe`, без эвристик по ID или масти.

### 9.6. Snapshot

При создании сохранить `content_version`, ID значений/комбинаций, текст каждой позиции, итог, ID карт/позиций и полный `snapshot_json`. История всегда возвращает snapshot, не пересобирает старый результат.

## 11. Backend API

REST JSON под `/api/v1`.

- `GET /health` — процесс жив.
- `GET /ready` — готовность и доступность БД без раскрытия секретов.
- `GET /api/v1/catalog` — активные темы, расклады, позиции.
- `POST /api/v1/auth/telegram` — проверка `initData`, upsert пользователя.
- `GET /api/v1/me` — профиль, Premium и лимит.
- `PATCH /api/v1/me/preferences` — разрешённые настройки уведомлений.
- `POST /api/v1/readings` — принимает `spread_code`, `theme_code`, nullable `question`, `idempotency_key`; проверяет права/лимит, вытягивает карты, строит текст и атомарно сохраняет результат.
- `GET /api/v1/readings/{reading_id}` — snapshot только владельцу.
- `GET /api/v1/history?limit=...&cursor=...` — история с серверным ограничением free.
- `DELETE /api/v1/readings/{reading_id}` — опционально; удаление не возвращает лимит и не удаляет платёжный учёт.
- `GET /api/v1/premium/products` — только активные тарифы.
- `GET /api/v1/premium/status` — entitlement.
- `POST /api/v1/payments/create` — invoice с серверной ценой и уникальным payload.
- Обработчик Telegram payment updates — подтверждение платежа.
- `GET /api/v1/payments/{payment_id}` — статус платежа владельца.

Пользовательские endpoint требуют Telegram auth, кроме явно публичных health/catalog. При Telegram Stars реализовать актуальный официальный invoice/pre-checkout/successful-payment flow. Premium выдавать только после подтверждённого `successful_payment`; сверять пользователя, payload, сумму и валюту. `pre_checkout_query` не означает оплату. Перед production проверить актуальные правила Telegram для цифровых товаров.

HTTP ошибки: 400 неверные параметры; 401 auth; 403 права; 404 отсутствующая/чужая запись; 409 конфликт лимита/idempotency/платежа; 422 валидация; 429 rate limit; 500 общая ошибка без деталей; 503 временная недоступность.

## 14. Python content-builder

Генератор структурирует контент, валидирует ссылки и экспортирует SQL/seed, но не придумывает экспертные значения.

Структура:
```text
content-builder/
├── build.py
├── config.py
├── models.py
├── tags.py
├── cards.py
├── rules.py
├── validators.py
├── sql_writer.py
├── content/{meanings.json,combinations.json,relations.json}
└── output/
```

Модели: `Card`, `TagCategory`, `Tag`, `CardTag`, `CardRelation`, `CardMeaning`, `CardCombination`, `InterpretationTemplate`.

`build.py`:
1. загрузить контент;
2. проверить схему, уникальность, FK и допустимые значения;
3. нормализовать только явно симметричные связи;
4. выявить дубли;
5. экспортировать SQL или согласованный seed;
6. вывести отчёт по числу сущностей, ошибкам и предупреждениям.

Одинаковый вход должен давать одинаковый результат. Стабильная сортировка; исходный контент не перезаписывать; при ошибке валидации ненулевой exit code; SQL безопасно экранировать; ID стабильны; `needs_review` не попадает в пользовательский результат.

Исторически обсуждались SQL-файлы:
`001_schema.sql`, `010_categories.sql`, `020_tags_events.sql`, `021_tags_emotions.sql`, `022_tags_relationships.sql`, `023_tags_career.sql`, `024_tags_finance.sql`, `025_tags_spiritual.sql`, `026_tags_actions.sql`, `027_tags_obstacles.sql`, `028_tags_personality.sql`, `029_tags_energy.sql`, `030_tags_time.sql`, `031_tags_result.sql`, `040_relations_tags.sql`, `041_cards.sql`, `042_card_relations.sql`, `050_card_meanings.sql`, `060_card_combinations.sql`.

Это история именования, не несколько параллельных схем. `041_cards.sql` задумывался как 78 карт с `(id, arcana, suit, number, code, name_ru, name_en)`. Фрагменты `042_card_relations.sql` для карт 1–8 и 9–16 — черновики, не завершённый проверенный файл.

**Последнее архитектурное решение:** вместо ручной записи тысяч SQL-вставок реализовать Python-генератор с моделями 78 карт, словарём тегов, явными правилами, редакционными значениями/комбинациями, валидацией и экспортом. Генератор ещё предстоит реализовать.

## 15. Монетизация

Модель: один обычный расклад в день бесплатно, ограниченная история; Premium — безлимит, Кельтский крест, полная история. Предпочтительный провайдер — Telegram Stars после проверки актуальных требований.

Тариф содержит `product_code`, название/описание, entitlement, длительность, целочисленную цену, валюту и `is_active`.

Процесс:
1. создать запись платежа;
2. создать invoice с уникальным payload;
3. проверить официальный callback;
4. сверить пользователя, payload, сумму и валюту;
5. пометить платёж оплаченным;
6. создать entitlement ровно один раз.

Повтор callback не должен дублировать выдачу доступа. Открытие invoice/pre-checkout не активирует Premium. Mock допустим только в тестах, не в production.

## 16. Редактура контента

CMS не обязательна. Контент редактируется в seed/БД. У блоков есть `is_active`, priority и review status. `needs_review`/`rejected` не показываются пользователю. Обновление контента не меняет snapshots. README объясняет добавление значений и запуск seed.

Админ API, если нужен, проверяет `ADMIN_TELEGRAM_IDS` из env; скрытая кнопка frontend не защита. Не создавать публичное редактирование контента.

## 17. Ошибки и крайние случаи

Обработать: невалидную/просроченную `initData`; открытие вне Telegram; недостаток активных карт; отсутствующий текст; исчерпанный лимит; Premium-only расклад у free; истёкший Premium; параллельные запросы; повтор после timeout; двойное нажатие; недоступную БД; незавершённый/дублированный платёж; неправильные сумму/валюту/payload; блокировку бота; старый snapshot после обновления контента; пустую историю; ограничение истории; HTML/script/emoji/длинный вопрос; отсутствующий placeholder; ненастроенные токены/URL/тарифы.

- Правильное количество уникальных карт.
- Кельтский крест требует Premium.
- Порядок позиций стабилен.
- Отсутствующий текст вызывает fallback, не 500.

- Повторный idempotency key не создаёт дубль.

### Лимит/Premium
- Free может создать один бесплатный расклад в день.
- Второй блокируется.
- Новый день в `APP_TIMEZONE` сбрасывает лимит.
- Premium не расходует лимит.
- Истёкший entitlement не даёт доступ.
- Параллельные запросы не обходят лимит.

### Платежи
- Invoice использует серверную цену.
- Invoice/pre-checkout не активирует Premium.
- Только успешная подтверждённая оплата создаёт entitlement.
- Дублированный callback не дублирует доступ.
- Неверные сумма/валюта/payload отклоняются.
- Без конфигурации покупка невозможна.

### UI/deploy
- Полный путь старт → расклад → тема → вопрос → результат → история.
- Видны состояния загрузки/ошибок.
- Premium показывает только активные тарифы.
- Оплата не имитируется.
- UI работает на мобильной ширине Telegram WebView.
- README позволяет чистую установку.
- Миграции, seed, `/health`, `/ready`, backend, frontend и бот работают.
- Критические тесты проходят, секретов в репозитории нет.
